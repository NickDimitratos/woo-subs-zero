# PAY.nl iDEAL signup and SEPA renewals

Introduced in 0.1.56, disabled by default. This is a general plugin integration: no customer, product, amount, sales location or number of months is fixed in source. Initial orders use the PAY.nl iDEAL gateway `pay_gateway_ideal` (option 10); bank renewal orders use the internal `wsz_paynl_sepa` gateway, which is not a checkout choice and does not expose iDEAL card/refund operations for bank debits. The installed PAY.nl gateway calls its separate Direct Debit checkout method `pay_gateway_incasso` (option 137); it is not a card-token gateway and is not automatically opted into this iDEAL signup flow.

## Merchant setup

1. Obtain PAY.nl approval for SEPA Direct Debit (payment option 137) on the intended sales location. PAY.nl documents Professional (S) or higher and boarding approval. Confirm the correct creditor identifier and mandate wording with PAY.nl. Enabling iDEAL or card tokenization does not enable bank collection.
2. Configure the existing PAY.nl WooCommerce plugin and its API credentials. In **WooCommerce → WSZ Subscriptions → Payment Gateways**, fill the SEPA creditor name/identifier, public mandate/contact/cancellation terms URL and advance-notice period, then explicitly enable PAY.nl SEPA. No credentials are stored in the new settings.
3. Use EUR subscriptions. Classic checkout is supported; the Checkout Block consent fields require WooCommerce 9.9+ and its additional-fields API. PHP Sodium and stable WordPress authentication salts are required for encrypted bank authorization. Keep normal WordPress, database and salt backups secure.
4. Ensure the dedicated callback `?wc-api=wsz_paynl_sepa` is publicly reachable and Action Scheduler and mail delivery work. The callback URL is sent with the mandate. Keep the existing PAY.nl initial-payment callback working too.
5. Complete merchant-approved staging acceptance before enabling real collections. PAY.nl's hosted-checkout test flag does not document protection for the mandate APIs. WSZ refuses SEPA bank API requests, including status checks and mandate deletion, when PAY.nl global/IP test mode or WSZ accelerated test mode is active. Automated tests mock HTTP and never send mandates, bank debits or emails.

## PAY.nl card callbacks

From 0.1.58, both WSZ card-token callback entry points require a verified callback before storing a token. The built-in verifier supports PAY.nl HMAC-signed JSON over the exact request body, checks the key and Sales Location, and links a documented transaction, order or session ID to the WooCommerce order. The configured PAY.nl AT-code/API-token pair is available as a signing key; a merchant integration may provide an SL signing secret using the `wsz_subs_paynl_token_signing_keys` filter. Never place a secret in theme code, a public repository or logs. A verified late callback can still establish automatic renewal after the initial card checkout; a stale callback cannot replace a changed payment method or newer card.

An unsigned legacy card-token callback is not accepted by default. Initial card checkout remains possible, but its subscription stays manual until reusable context is securely verified. Existing valid saved card tokens remain usable. If PAY.nl uses a different authenticated card notification format for the merchant, an integration can implement `wsz_subs_verify_paynl_token_exchange`; returning `true` must mean it has independently verified the entire raw exchange against PAY.nl and the merchant. Order/customer and provider-reference checks still apply. A generic PAY.nl order-status exchange also requires a matching signed JSON order body or an explicitly trusted `wsz_subs_verify_gateway_exchange` implementation; a customer order key alone is not payment verification.

Confirm the card-token exchange format and signing keys with PAY.nl and test a late token callback in staging before rollout. PAY.nl documents that signed JSON is not yet supported for direct-debit exchanges; the dedicated SEPA path verifies those by authenticated status queries. Do not switch a whole Sales Location's exchange format without confirming with PAY.nl that both the existing initial-payment callback and the bank callback will continue to work. Successful automated mocks do not establish that configuration.

## Checkout and billing

For a subscription paid initially with iDEAL, checkout asks for the account holder, IBAN, BIC and a separate, unchecked mandate-consent checkbox. Consent includes creditor identity, the distinction between initial iDEAL and later SEPA, the displayed subscription terms, notice period, refund wording and the mandate terms URL. Ordinary carts and card payments do not require these fields.

Bank details and consent evidence (customer, time, IP, displayed consent text, original notice period, creditor and sales location) are encrypted in private order metadata. Plaintext Block additional-field copies are removed before order persistence, including draft PUT requests. Partial draft fields are kept in a separate encrypted blob and restored through WooCommerce field defaults; a draft checkbox is not authorization. The encrypted draft is removed on final checkout or when switching away from iDEAL. Authorization is copied to a subscription only when that subscription is explicitly linked to the same customer’s paid iDEAL parent order. Gateway registration, an order key, a card token or a successful iDEAL payment alone cannot create this bank authorization. When the native PAY.nl plugin exposes its cached options, option 137 must also be available before checkout can advertise this flow or initial automatic setup can complete. The cache is not proof of merchant approval or live API permission; confirm those with PAY.nl. A later card-method change, manual-renewal choice or cancellation is preserved.

WSZ owns the billing schedule. It prepares a renewal before its due date using the configured notice period, sends the customer the actual EUR renewal order total, collection reference, masked account and PAY.nl processing date, and requests that processing date. The notice defaults to 14 days; shorten it only when the customer agreement permits. Existing authorizations retain their original minimum notice period. If checkout/queue timing cannot provide enough advance notice, processing is delayed to preserve that period. Bank debit/settlement follows PAY.nl processing and is not instantaneous.

Amounts include what WooCommerce put on that renewal order, including quantity, tax and applicable discounts/adjustments. `wsz_subs_renewal_amount` still applies before dispatch and updates that order total. A prepared order and its announced amount are fixed for that collection. Later changes follow the existing WooCommerce/WSZ subscription pricing rules: changing a catalog price alone does not rewrite an already contracted subscription amount. Zero-total renewals complete without submitting a bank debit. Non-EUR, negative/sub-cent amounts or invalid context require recovery without a bank request.

At the **first bank renewal**, WSZ creates a **FLEXIBLE** mandate. PAY.nl automatically creates that mandate's first debit, so WSZ does not also call DirectDebit:Add for the same cycle. There is no extra SEPA debit at signup. The mandate is not treated as active until its first debit is verified as successful. Later cycles call DirectDebit:Add once, with the corresponding renewal order's amount and the subscription's finite/open-ended terms. PAY.nl does not run a second recurring schedule.

Orders remain **on hold** during bank processing. No customer Pay button or card retry is offered while an accepted/uncertain collection remains pending. A verified debit status 100 completes the cycle once; 91/526/processed states remain pending. Status 97, 103, 106 or 127 stops collection and requires review. Failed/refused/reversed debits stop automatic collection and require review, including reason 109: WSZ deliberately does not automate bank retries. A later reversal does not automatically undo historical billing dates; reconcile the ledger and outstanding balance before recovery. If PAY.nl later reports a failed/reversed debit as collected, WSZ blocks another customer payment and flags the order for review rather than reopening it automatically.

## Verification, cancellation and recovery

An exchange is only a hint. WSZ authenticates a GET to PAY.nl and checks the debit ID, mandate, sales location, renewal reference, EUR amount and currency before applying bank status. For a first debit that omits `extra1`, the callback URL supplies an untrusted order hint and WSZ also verifies the mandate reference and account with an authenticated GET. An ambiguous create is never submitted again; the same callback can recover it after both provider objects match. The first IL debit ID is discovered through the PAY.nl exchange. The generic WSZ webhook cannot mark a SEPA order paid, even with a customer order key or a card verification filter.

The submission intent and pending order are saved before the HTTP request. A timeout or malformed response may mean PAY.nl accepted it: the order stays on hold with a review note and is **never automatically resubmitted**. Repeated dispatch, duplicate exchanges and scheduled jobs cannot create another bank request for that order. A verified later exchange can recover the initial IO/IL references after an uncertain response. A poll retries read-only reconciliation; if the first IL exchange never arrived, repair callback delivery and obtain the matching provider references instead of guessing or resubmitting.

On completion of all required payments, cancellation, expiry, pending cancellation or a switch away from the original iDEAL method, WSZ locally revokes bank authority and asks PAY.nl to delete the flexible mandate. Failed or ambiguous revocation, including HTTP 404 or a changed Sales Location, is recorded for review and retried; only confirmed successful deletion is marked revoked at the provider. A debit already submitted to a bank batch may still settle: the subscription note explicitly calls for PAY.nl review, and a late paid callback does not revive a cancelled subscription. No automatic refund or unverified cancellation of an existing batch is attempted.

For an affected **existing iDEAL subscription**, preserve the paid signup and any paid renewals. The 0.1.55 safety behavior remains: unsupported legacy subscriptions fall back to manual payment without repeated card-token attempts. Enabling SEPA does not manufacture consent, reuse an iDEAL transaction as a mandate or migrate old subscriptions. Obtain fresh customer authorization through an approved migration flow, or recover using an already supported card-payment update. This release supplies SEPA consent at new subscription checkout; it does not add a bulk migration or a standalone mandate-enrollment screen for old contracts. Never create a second paid signup merely to repair an existing renewal.

The renewal order action **Refresh PAY.nl SEPA bank status** performs authenticated reconciliation when its IL reference is known. It never resubmits a collection. If the first IL has not arrived, it records that callback delivery needs repair.

For an uncertain bank order, inspect the renewal/subscription notes and the exact IO/IL references in PAY.nl. Reconcile accepted transactions first; preserve pending markers until it is established that no duplicate collection can occur. Changing a flag to automatic, removing a token error or simply replaying a POST is not recovery. A stale process lock after a terminated worker also needs operator review after checking the provider outcome; do not unlock and resubmit blindly.

## Finite payments and service expiry

From 0.1.57, receiving the final required payment stops billing and clears the next-payment date, but preserves active service until the stored subscription end date. For example, a six-month term starting 22 October has payments on 22 October through 22 March, and expires on 22 April. The last payment buys the final month. This follows the product/subscription interval, payment count and end date; no dates or amounts are fixed in the integration.

WSZ rejects stale renewal keys, cancels future renewal/preparation jobs and revokes the flexible bank mandate after the final settlement. It retains the end-of-service expiration job. Stale dispatch, card retries, early renewal and repeated settlement callbacks cannot create a seventh charge. If the final payment settles at or after the stored end date, expiry happens then; the term is not extended from the settlement date. Existing cancellation and late-settlement safeguards remain in effect.

The defect was reproduced with ten failing regression cases before the fix. The local integration test uses real WooCommerce persistence and fully mocked iDEAL/bank responses, with external HTTP and email blocked. It does not prove PAY.nl merchant acceptance or bank settlement. See the operations playbook for review of subscriptions already marked expired by older versions.

## Extension points

- `wsz_subs_subscription_payments_completed` receives the fully paid subscription when billing ends, independently of later service expiry. Payment providers can stop their collection authority without ending prepaid service.

- `wsz_subs_automatic_renewal_gateway_ids`: includes configured card adapters, the enabled WSZ test gateway and the iDEAL + SEPA capability. Custom themes/checkouts should use this capability when deciding which initial methods allow automatic subscriptions. A theme that only allows `wsz_subs_tokenized_gateway_ids` will continue hiding iDEAL until its own integration adopts the new capability.
- `wsz_subs_tokenized_gateway_ids` / `wsz_subs_paynl_gateway_ids`: keep their card-token meaning. Do not add iDEAL to these filters to enable bank renewals.
- `wsz_subs_paynl_recurring_credentials`: existing store credential resolution is reused. `wsz_subs_paynl_sepa_credentials` can customize bank request credentials with the order and subscription context; it must return the same authorized Sales Location during checkout, subscription validation and renewals. Capability discovery can pass an unsaved checkout order, so extensions must not depend on its order ID.
- `wsz_subs_paynl_sepa_consent_text`: filter the displayed and recorded plain-text authorization wording. Merchants must use wording approved for their agreement; empty or invalid text disables the SEPA checkout capability.
- `wsz_subs_paynl_sepa_provider_available`: override the native gateway's cached option-137 availability check for an explicitly verified custom integration. The filter must not be used to claim approval that the merchant does not have.
- `wsz_subs_paynl_token_signing_keys` and `wsz_subs_verify_paynl_token_exchange`: configure trusted card callback signing keys or a separately authenticated card-token verifier as described above. `wsz_subs_verify_gateway_exchange` is the existing extension point for a separately verified generic payment status.
- `wsz_subs_paynl_sepa_send_notice`: return `null` for the standard mailer, or a boolean after a custom notification system handles the notice. False prevents submission. A custom implementation must actually issue the agreed collection notice.
- `wsz_subs_async_renewal_payment_complete`: used internally after authenticated settlement; handlers must tolerate retries until `_wsz_cycle_completed` is committed. It is not an externally callable payment-verification endpoint.

## Verification performed

The initial five SEPA feature checks failed before implementation because no SEPA integration existed. A separate pending-bank renewal regression failed because the renewal engine marked it failed. A generic-webhook fixture also demonstrated an unverified `paid` transition before the bank-path exclusion, then remained on hold afterward.

Focused coverage includes encrypted consent/ownership, classic and Store API input, independent card/bank classification, varied amounts, first/subsequent debit creation, pending/uncertain responses, authenticated/mismatched exchanges, duplicate settlement, cancellation/reversal and blocked retries. Renewal engine checks include monthly, annual and fortnightly periods, configured finite counts and resumed accounting. Existing Stripe, Mollie and card tests run in the full suite.

Run `./vendor/bin/phpunit -c phpunit.xml.dist`, `node --test tests/checkout/paynl-block-checkout.test.js`, `composer run lint`, `composer validate --strict`, and `git diff --check`. Browser QA used a separate, non-submitting Chrome preview of the actual field definitions and visibility script; it was not a full WordPress checkout or a bank acceptance test. Conditional field schemas were additionally checked with the installed WooCommerce 10.7 Opis validator. No production changes or live payments were made.

A later 0.1.57 smoke test used the actual PAY.nl hosted iDEAL sandbox from localhost, with a synthetic customer and a EUR 50 subscription signup. An authenticated provider lookup verified PAID (100), test mode, the exact amount, currency, sales location and order reference. Because PAY.nl cannot deliver its exchange to localhost, that verified response was passed to the existing PAY.nl plugin's normal transaction processor; the Woo order became paid and WSZ activated the subscription with one of six payments counted. No local order was marked paid merely from a return URL or an unverified callback.

This sandbox test deliberately permitted manual renewal for its isolated test cart. It did not enable SEPA, establish a mandate, or verify bank renewals. The subscription correctly remained manual with no token or bank authorization. The synthetic subscription and its future jobs were stopped after verification; the paid signup was retained. Existing order, stored-setting and administrator billing-profile fingerprints were unchanged. Public exchange delivery and real merchant-approved SEPA acceptance remain unverified.
